### Finding 3 is conditional, and the condition is the roofline

Once every run uses an L2-safe shape, the exception stops looking like noise. `q4_0` wins exactly where the `q8_0` kernel is already at the memory roof, and loses everywhere it is not:

| device | q8_0 as fraction of its measured roof | q4_0 / q8_0 time | which format wins |
|---|---|---|---|
| NVIDIA L4 (run 1) | 95.8% | 0.66x | **q4_0** |
| NVIDIA L4 (run 2) | 95.7% | 0.71x | **q4_0** |
| NVIDIA GeForce RTX 3050 Laptop GPU | 72.1% | 1.16x | q8_0 |
| NVIDIA A100-SXM4-40GB (run 1) | 70.9% | 1.70x | q8_0 |
| Tesla T4 (run 1) | 70.7% | 1.64x | q8_0 |
| NVIDIA A100-SXM4-40GB (run 2) | 70.5% | 1.71x | q8_0 |
| Tesla T4 (run 2) | 68.3% | 1.56x | q8_0 |
| Tesla P100-PCIE-16GB (run 1) | 62.4% | 1.35x | q8_0 |
| Tesla P100-PCIE-16GB (run 2) | 62.3% | 1.35x | q8_0 |

Every run in which `q8_0` reaches 96% of its roof has `q4_0` winning. Every run in which it reaches at most 72% has `q4_0` losing. The profiler agrees: on the one machine where `q4_0` wins, the `q8_0` kernel reads DRAM at 95.7% of peak, so there is nothing left to gain from the memory system and the only way forward is to move fewer bytes.

**Fewer bytes buys time only once you are actually bandwidth bound.** Below the roof the unpacking arithmetic costs more than the bytes save. This supersedes the flat claim that four-bit weights are simply slower, which was true of every machine measured until one got close enough to its roof to falsify it. That is the argument for measuring more than one machine, and it is the second claim in this study to survive only in a narrower form than it was first written in.

   - NVIDIA L4: 41.6x more sectors

   **Confirmed.** Same weight bytes, same arithmetic, and the slow kernel issues over forty times the load sectors. That is a 32-way gather on the activation vector and nothing else.

2. `q8_v5_soa_smem` should show the highest DRAM throughput of the `q8_0` set. **Confirmed** on every profiled device.

3. `q4_0` should be ALU bound rather than memory bound. The compute-to-memory throughput ratio, best kernel of each format:

It is worth being precise about what is not confirmed: the ratio exceeds 1.0, meaning compute actually dominates, on some devices and not others.

## The advance prediction, and its retraction

fp32 FMA peak below is SMs x cores per SM x 2 x clock. Cores per SM is an architectural constant rather than a measurement, and the balance column divides it by the measured roof, so for the cache-resident parts that denominator is wrong too.

| | NVIDIA GeForce RTX 3050 Laptop GPU | NVIDIA L4 (run 1) | NVIDIA L4 (run 2) | Tesla T4 (run 1) | Tesla T4 (run 2) | Tesla P100-PCIE-16GB (run 1) | Tesla P100-PCIE-16GB (run 2) | NVIDIA A100-SXM4-40GB (run 1) | NVIDIA A100-SXM4-40GB (run 2) |
|---|---|---|---|---|---|---|---|---|---|
| fp32 peak (TFLOP/s) | 4.33 | 30.29 | 30.29 | 8.14 | 8.14 | 9.52 | 9.52 | 19.49 | 19.49 |
| balance (FLOP per byte) | 25.3 | 117.3 | 117.3 | 29.7 | 29.7 | 15.9 | 15.9 | 13.8 | 13.7 |
| finding 3: q4_0 / q8_0 time | 1.16x | 0.66x | 0.71x | 1.64x | 1.56x | 1.35x | 1.35x | 1.70x | 1.71x |

The prediction, written down after the laptop run and before any cloud run: finding 3 is an ALU-bound story, so the `q4_0` penalty should be **worse on the machine with less compute per byte of bandwidth**.

| device | balance (FLOP/byte) | q4_0 penalty |
|---|---|---|
| NVIDIA A100-SXM4-40GB | 13.8 | 1.70x |
| Tesla P100-PCIE-16GB | 15.9 | 1.35x |
| NVIDIA GeForce RTX 3050 Laptop GPU | 25.3 | 1.16x |
| Tesla T4 | 29.7 | 1.64x |
| NVIDIA L4 | 117.3 | 0.66x |

Pearson correlation across 5 devices: **r = -0.85**, and the ordering is not monotonic.

**The prediction is withdrawn.** On two devices it looked confirmed. With five it is not: NVIDIA A100-SXM4-40GB has the *lowest* balance of the set and a penalty of 1.70x, while NVIDIA L4 has the highest balance and the largest penalty at 0.66x, which is the opposite of what was predicted.

Two caveats make the retraction firmer rather than softer. Two of the five are cache resident, so their measured roof is not the denominator their kernels actually saw. And a two-point trend that dies on the third point is exactly the failure mode this project has hit before.

What survives is the part the profiler measured directly: the `q4_0` penalty is real on every device tested, and its mechanism is the unpacking arithmetic. What does not survive is any claim to predict its size from a datasheet.
